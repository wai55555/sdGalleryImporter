## §0 前提指示（作業規約）

### 0.1 役割と進め方
- あなたは実装担当である。設計判断は本書に従い、本書にない判断が必要になったら、推測で進めず、その判断点だけを切り出してユーザーに確認すること。
- **1フェーズ = 1ブランチ = 1PR（または1コミット群）**。複数フェーズを同時に混ぜない。
- コミットとプッシュは実装者が行う。コミットメッセージは対象リポジトリの既存 `git log` を確認し、その形式・文体に合わせる（前例のない形式を新しく作らない）。PR の作成とマージはユーザーの作業。
- 各フェーズの完了条件（§10）を満たしたことをテストで示してから次へ進む。

### 0.2 本ツールの位置づけ
- 本ツールは新規リポジトリの Rust 単体 exe とする。名前は `sdGalleryImporter`（exe 名も同じ）。
- 依存する既存資産は2つだけであり、いずれもバージョンを固定する：
  - **fast_meta v2.1.0**（画像メタデータ抽出ライブラリ、`checkImageMetadata` リポジトリの git tag `v2.1.0` をライブラリとして取り込む。子プロセスで exe を起動しない）。ライブラリが公開する整形関数 `extract_to_writer` を使い、CLI と同一の出力テキストを得る（REQ-5.2。ただし見出し行のパス表記は渡したパス文字列そのままになるため、「同一」は絶対パスで CLI を実行した場合の出力との同一を指す）。走査オプション（`ScanOptions`）は txt 生成・抽出の双方で既定値（strict = false、stealth = Auto）を用い、変更しない（出力同一性の前提）。
  - **取り込み先 SQLite**（§4）。フロントエンドと共有する正本 DB であり、本ツールはそのスキーマの一部（§4.3 の追加分を含む）を前提とする。
- 本ツールは画像ファイルを一切移動・コピー・改変しない。書き込みは txt サイドカー（§5）と DB とログファイル（§8.3）だけである。画像の仕分けは別ツール（sdMetaImageSorter）の領分であり、本ツールに混ぜない。
- 実行環境は Windows を前提とする（パスの扱いは §9.1 の正規化規則による）。

## §1 目的と非目的

### 1.1 目的
既にストーリーとして売られている、メタデータ入りの AI 画像 CG 集を「お手本」として取り込むこと。具体的には、ギャラリー（フォルダ）単位で以下を同時に行う：

1. 各画像のメタデータを抽出し、画像ごとのサイドカー txt としてギャラリー内に記録する（§5）。
2. 同時に DB へ取り込み、ギャラリー＝ストーリーとして再利用可能な形にする（§4、§7）。

お手本の使い方は2通りある（どちらも本ツールの取り込み対象として成立させる）：
- (1) そのまま再現する（キャラ・画風込みの全文プロンプトで回す）。
- (2) 自分のキャラ・画風に差し替えて使う（層分解は本ツールの外で行う。§1.2、§4.3 の `derived_from_line_id`）。

### 1.2 非目的（捨てたもの）
- **層分解（全文からキャラ・画風・品質を取り除いてシチュエーションだけにすること）は本ツールで行わない。** 取り込みは全文のまま。分解したくなったら、分解結果を新しい行として作り、元行へのリンク（`derived_from_line_id`）を張る運用であり、その操作はフロントエンド側／手作業の担当。本ツールは器（列）だけ用意する。
- **試行回数・難易度の推定はしない。** 売り物の CG 集は AI 絵特有の打率でハズレを除去済みであり、残った枚数から元の試行回数は原理的に復元できない。復元できるのは「発表された枚数」だけであり、それは §7 の segment / repeat として扱う。
- **seed は参照しない。** 同じモデル／ワークフローを使うわけではないため、seed を DB の列・照合キー・代表選定に一切使わない。seed を見たくなったら txt を見る（txt には抽出結果がそのまま残る）。
- **差分画像（同一シチュエーションの微差分）の検出はしない。** そのような混入はまず無い前提とする。
- **プロンプト文字列の正規化はしない**（REQ-7.2）。表記ゆれが実際に観測されたら、その時点で別途導入を検討する。本書の範囲では入れない。
- **Stealth 埋め込み（PNG の `stealth_pnginfo` / `stealth_pngcomp`）からの pos/neg 抽出は対象外とする。** fast_meta は Stealth レコードを返すが、本ツールでは §6 の抽出入力に含めない。Stealth しかメタデータが無い画像は未抽出として扱う（txt には Stealth レコードも出力されるので、人が読む記録としては残る）。
- **InvokeAI の旧 `Dream` キー（コマンドライン文字列形式）は対象外とする。**
- 画面（GUI）は持たない。起動は exe へのドラッグ＆ドロップ（D&D）が主経路（§8.1）。

## §2 全体設計

### 2.1 処理パイプライン（1回の実行）
```
引数のフォルダ群（D&D で複数可）
  → フォルダごとに:
      ギャラリー境界の決定（§3）
      → ページ列挙（直下のみ、ファイル名の自然順）
      → fast_meta でメタデータ抽出
      → txt サイドカー出力（§5）
      → pos/neg 抽出（形式別、§6）
      → segment 化（§7）
      → DB 書き込み（§4）※ --dry-run 時は書かない
  → ログファイルへ実行サマリを出力（§8.3）
```
- フォルダは順次処理する。**1フォルダの失敗で全体を止めない。** 失敗したフォルダはログに記録して次へ進む。
- 入力フォルダは、別ツール（sdMetaImageSorter）で整理済みのフォルダをそのまま渡される想定である。本ツール側で仕分け直しはしない。
- 同じフォルダが1回の実行の引数に重複して渡された場合は、正規化パス（REQ-9.1）で重複を除き、1回だけ処理する。
- 引数にフォルダでないもの（ファイル等）が混ざっていた場合は、その引数を無視し、ログに記録する。

### 2.2 ギャラリー＝ストーリー
- 取り込みと同時に「1ギャラリー（リーフ） = 1ストーリー（下書き）」を生成する（§4.4）。ステージング用の別 DB は挟まない。コンテナ（親）ギャラリーはストーリーを生成しない（REQ-3.2）。
- 取り込んだストーリーの層（品質／画風／キャラ）は空である。だから配置された行の全文がそのまま最終プロンプトになり、「そのまま再現」が成立する。

### 2.3 速さ・軽さ
- メタデータ抽出は fast_meta ライブラリのインメモリ処理で行い、画像1枚ごとの子プロセス起動はしない。
- 大量の複数フォルダ（数千〜数万枚規模）を現実的な時間で処理できることを Phase 0 で実測する（§10）。

## §3 ギャラリー境界とページ順

### 3.1 境界（柔軟であること）
ギャラリーの境界はケースにより変わるため、仕様としては以下の規則で柔軟に対応する：

- **REQ-3.1** 引数で渡されたフォルダは、原則として1ギャラリー（リーフ）とする。
- **REQ-3.2** 渡されたフォルダの直下に画像ファイル（REQ-3.8 の拡張子で列挙されるファイルを指す）が1枚も無い場合は、そのフォルダ自体は**コンテナ**として扱う：`galleries` 行は作るが、ページ・segment・ストーリーは作らず（`story_id = NULL`）、サブフォルダ群を子ギャラリーとして再帰的に処理する（深さに上限は設けない。各サブフォルダに同じ規則を適用する）。直下に画像があるフォルダはリーフとして処理する。これにより D&D でもフラグ無しで両方の落とし方に対応する。再帰ではフォルダの実パス（REQ-9.1 の canonicalize 結果）で訪問済みを管理し、ジャンクション／シンボリックリンクによる循環は辿らない（訪問済みの実パスに再到達したらスキップし、ログに記録する）。
- **REQ-3.3** `--recursive` を指定した場合は、直下に画像があるフォルダもリーフとして処理しつつ、そのサブフォルダも子ギャラリーとして再帰処理する。
- **REQ-3.4** リーフギャラリーのページ列挙は**そのフォルダの直下のみ**（非再帰）とする。`--recursive` 無しでリーフ内にサブフォルダがある場合、その中身はこのギャラリーのページに含めず、無視したサブフォルダ名と件数をログに記録する。
- **REQ-3.5（不変条件）** segment（§7）の run はフォルダ境界を越えない。
- **REQ-3.6** 直下の画像が0枚でサブフォルダも無いフォルダ（空フォルダ）は、ギャラリー行を作らず、ログに記録してスキップする。この規則は REQ-3.2 のコンテナ扱いより優先する（画像0枚のフォルダでも、サブフォルダが無ければコンテナにはしない）。判定は画像ファイルとサブフォルダの有無だけで行い、画像以外のファイル（txt 等）の有無は影響しない。なお、コンテナとして処理を始めたフォルダのサブフォルダがすべて空で、結果的に子ギャラリーが1つもできなかった場合でも、先行して作ったコンテナ行は残す（後から子フォルダが増えたときに再利用される）。

### 3.2 ページ順と列挙
- **REQ-3.7** ページ順はファイル名の自然順のみで決める。リネームはしない。ページの同一性は元のファイル名そのものである。自然順の定義：ファイル名を「数字の連続」と「それ以外」に交互に分割し、チャンクごとに比較する。ここで「数字」とは ASCII の 0-9 のみを指す（全角数字は通常文字として扱う）。数字チャンク同士の比較は、先行ゼロを取り除いたうえで「長い方を大きい」とし、同長なら辞書順とする（数値型へ parse しないため、長大な数字列でも一意に定まる。数値として同値で元の表記だけ違う場合は、桁数が小さい方を先とする）。非数字チャンク同士は Unicode コードポイント順で比較する（大小文字は区別する）。同位置のチャンクが数字と非数字で食い違う場合は、数字チャンクを先とする。全チャンクが同値の場合はファイル名全体のコードポイント順で決める。一方のチャンク列が他方の接頭辞になる場合（例：`a` と `a1`）も、この最終規則（ファイル名全体のコードポイント順）を適用する。
- **REQ-3.8** 列挙のフィルタは拡張子で行う：`.png` / `.jpg` / `.jpeg` / `.webp`（大小文字は区別しない）。それ以外のファイルはページとして数えない。実際の形式判定は拡張子ではなく内容（マジックバイト）ベースで fast_meta が行うため、拡張子が対象でも内容が画像でないファイルは「読めない画像」として扱う（REQ-9.4）。

## §4 DB スキーマ

取り込み先はフロントエンドと共有する SQLite 1ファイル。§4.1〜§4.2 は共有スキーマのうち本ツールが読み書きする部分の定義（自己完結のため本書に記載する）。§4.3 は本ツールが追加する部分、§4.4 は本ツールが取り込み時に生成するものの定義である。

### 4.1 共有スキーマ：行マスタ / ストーリー / 配置

```sql
lines(                        -- 行マスタ（シチュエーションの実体）
  id INTEGER PRIMARY KEY,
  prompt TEXT NOT NULL,       -- positive
  negative TEXT NOT NULL DEFAULT '',
  width INTEGER, height INTEGER,
  tags TEXT,                  -- 検索用タグ（本ツールでは空でよい）
  archived INTEGER NOT NULL DEFAULT 0
)

stories(                      -- ストーリー（品質／画風／キャラの3層を持つ）
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  quality_prompt TEXT NOT NULL DEFAULT '',  quality_negative TEXT NOT NULL DEFAULT '',
  style_prompt TEXT NOT NULL DEFAULT '',    style_negative TEXT NOT NULL DEFAULT '',
  character_prompt TEXT NOT NULL DEFAULT '', character_negative TEXT NOT NULL DEFAULT '',
  workflow TEXT, seed_base INTEGER,
  status TEXT NOT NULL DEFAULT 'draft'
)

placements(                   -- 配置（ストーリー内での行の使われ方）
  id INTEGER PRIMARY KEY,
  story_id INTEGER NOT NULL REFERENCES stories(id),
  line_id INTEGER NOT NULL REFERENCES lines(id),
  ord INTEGER NOT NULL,       -- 並び順。0始まり（REQ-4.5）
  repeat INTEGER NOT NULL DEFAULT 1,        -- 数値。行マスタではなく配置の属性
  extra TEXT NOT NULL DEFAULT '', extra_neg TEXT NOT NULL DEFAULT ''
)
```

結合規則（参考。本ツールの責務ではないが前提として記載）：最終プロンプトは 品質 → 画風 → キャラ → 行 → 配置 extra の順に `, ` で結合する。取り込んだストーリーは3層が空なので、行の全文がそのまま効く（§2.2）。

### 4.2 行の照合（ハッシュ）
- **REQ-4.1** 行の同一性は **pos＋negative ペアのハッシュ**で照合する。`prompt_hash = SHA-256(prompt || "\x00" || negative)` とし、文字列は **UTF-8** でエンコードし、ハッシュは**小文字16進**で格納する。`pages.prompt_hash` も同一の定義である。
- pos だけのハッシュにしてはいけない。pos が同じで negative が違うものは別の行である（REQ-7.3 の segment 規則と一致させるため）。主取り込み元の NovelAI は negative（Undesired Content）が通常空ではないため、これは例外ではなく日常ケースである。
- **REQ-4.2** 照合で一致したら新規行を作らず、既存行への配置にする。これはギャラリーをまたいでも同じである。

### 4.3 本ツールが追加するテーブル・列

```sql
import_runs(                  -- 取り込みの実行記録（ログファイルと対応）
  id INTEGER PRIMARY KEY,
  started_at TEXT NOT NULL, finished_at TEXT,
  log_path TEXT,
  gallery_count INTEGER NOT NULL DEFAULT 0,
  page_count INTEGER NOT NULL DEFAULT 0,
  segment_count INTEGER NOT NULL DEFAULT 0,
  unextracted_count INTEGER NOT NULL DEFAULT 0
)

galleries(
  id INTEGER PRIMARY KEY,
  parent_id INTEGER REFERENCES galleries(id),
  root_path TEXT NOT NULL UNIQUE,           -- 正規化済み絶対パス（REQ-9.1）。再取り込み判定はこの一意性で担保
  name TEXT NOT NULL,                       -- フォルダ名（元の表記のまま）
  story_id INTEGER REFERENCES stories(id),  -- リーフのみ。コンテナは NULL（REQ-3.2）
  import_run_id INTEGER REFERENCES import_runs(id),
  imported_at TEXT NOT NULL
)

pages(
  id INTEGER PRIMARY KEY,
  gallery_id INTEGER NOT NULL REFERENCES galleries(id),
  file_name TEXT NOT NULL,                  -- 元ファイル名そのまま
  seq INTEGER NOT NULL,                     -- 自然順での位置（0始まり）
  width INTEGER, height INTEGER,            -- 画像の実寸（REQ-6.5。取れない場合は NULL）
  source TEXT NOT NULL,
    -- novelai / comfyui / a1111 / swarmui / invokeai : 生成元が判定できた（抽出の成否は prompt_hash の有無で示す）
    -- unknown : メタデータはあるが生成元が判定できない
    -- none    : 読めたがメタデータが無い
    -- error   : ファイルが読めない・壊れている
  prompt_hash TEXT,       -- 抽出できた場合のみ（定義は REQ-4.1）。それ以外は NULL
  segment_id INTEGER REFERENCES segments(id),  -- segment を作らないページは NULL（REQ-7.5）
  txt_status TEXT NOT NULL,
    -- written / fallback_metadata / skipped_exists / overwritten / failed / none（§5）
  UNIQUE(gallery_id, file_name)   -- 列挙は直下のみ（REQ-3.4）なので file_name で一意になる
)

segments(
  id INTEGER PRIMARY KEY,
  gallery_id INTEGER NOT NULL REFERENCES galleries(id),
  seq INTEGER NOT NULL,                     -- ギャラリー内での出現順（0始まり）
  run_length INTEGER NOT NULL,              -- 連続枚数。ここに永久保持する
  line_id INTEGER NOT NULL REFERENCES lines(id),
    -- segment は pos/neg が抽出できた run についてのみ作る（REQ-7.5）ため、line_id は常に非 NULL
  prompt_full TEXT NOT NULL, negative_full TEXT NOT NULL,  -- 抽出全文の控え（行が再利用されても残る）
  width INTEGER, height INTEGER,            -- 先頭ページの実寸
  UNIQUE(gallery_id, seq)
)
```

既存テーブルへの列追加：
```sql
ALTER TABLE lines ADD COLUMN prompt_hash TEXT;            -- REQ-4.1
ALTER TABLE lines ADD COLUMN derived_from_line_id INTEGER REFERENCES lines(id);  -- 分解の派生行用（§1.2）
ALTER TABLE lines ADD COLUMN origin TEXT;                 -- 'cg_import' / 'llm' / 'manual'
ALTER TABLE placements ADD COLUMN segment_id INTEGER REFERENCES segments(id);   -- 出自の追跡
ALTER TABLE stories ADD COLUMN origin_gallery_id INTEGER REFERENCES galleries(id);
CREATE INDEX idx_lines_prompt_hash ON lines(prompt_hash);
```
- **REQ-4.3** スキーマの作成・列追加は本ツールの起動時に冪等に行う（存在チェックをしてから作る）。既存 DB に対して破壊的変更（列削除・型変更）はしない。あわせて以下を必ず行う：
  - 接続ごとに `PRAGMA foreign_keys = ON` を実行する（SQLite の外部キーは接続単位で有効化しないと効かない）。実行タイミングは**接続直後、トランザクション開始前**と固定する（この pragma はトランザクション内では変更が効かないため）。
  - 既存の `lines` 行で `prompt_hash` が NULL のものは、その場で REQ-4.1 の定義により計算して埋める（バックフィル）。これをしないと本ツール以前に作られた行が照合に一切掛からない。
  - `prompt_hash` の索引は**一意索引にしない**（共有スキーマ上、同文の行が複数存在することは合法であり、一意化できなくても照合は可能だから）。バックフィル後に同一 `prompt_hash` を持つ既存行が複数あっても異常終了せず、ログに警告を残して続行する。照合で複数行が一致した場合は、最小の `id` の行を採用する（決定的にするため）。
  - スキーマ用意・バックフィル・索引作成は**全体を1トランザクション**で行う。異常終了した場合はロールバックされ、バックフィルだけが残るような中途半端な状態にはならない。
  - 日時列（`import_runs.started_at` / `finished_at`、`galleries.imported_at`）は ISO 8601 形式で、実行環境のローカル時刻（タイムゾーンオフセット付き）で記録する。
- **REQ-4.4** DB 書き込みのトランザクション単位は**リーフギャラリー1件**とする（コンテナ配下全体を1単位にはしない）。途中で失敗したらそのリーフ分はロールバックする（半端なギャラリーを残さない）。他ギャラリーの取り込み済み分には影響させない。コンテナ行の INSERT は、配下の子の処理に先立って単独のトランザクションで確定させる。同じフォルダに複数経路で到達した場合（引数として直接渡され、かつ別の引数コンテナの配下でもある等）は、既存の `galleries` 行を再利用し、`parent_id` は最初に作られた値を変更しない。
- **REQ-4.5** 1つのリーフギャラリーの取り込みで生成するのは：`galleries` 1件、`pages` ページ数分、`segments` segment 数分、`stories` 1件（title はフォルダ名、3層は空、`status = 'draft'`、`origin_gallery_id` を設定）、`placements` segment 数分（`ord` は対応する segment の `seq` と同値＝0始まり、`segment_id` を設定、`repeat` は REQ-7.7）。コンテナギャラリーでは `galleries` 行のみを生成する。
  - 生成順序（外部キー制約のため固定する）：(1) `galleries` を `story_id = NULL` で INSERT、(2) `stories` を `origin_gallery_id` にその gallery の id を入れて INSERT、(3) `galleries.story_id` を UPDATE で埋める、(4) `lines` を照合・新規作成、(5) `segments` を INSERT（`line_id` は (4) を参照）、(6) `pages` を INSERT し `segment_id` を埋める、`placements` を INSERT（`segment_id` は (5) を参照）。
- **REQ-4.6** 行は REQ-4.2 の照合で再利用または新規作成する。新規行の `origin` は `'cg_import'`、寸法は segment 先頭ページの実寸とする。

## §5 txt サイドカー

txt は「記録」である。目的は2つ：(a) そのギャラリーを取り込み済みかどうかが人の目で分かること、(b) 後から気に入った画像があったとき、その画像のメタデータを fast_meta を再実行せずにすぐ見られること。

- **REQ-5.1** txt は**画像ごとのサイドカー**とする。画像 `001.png` に対して `001.txt` を同じフォルダに出す。ギャラリー全画像分をまとめた索引ファイル（`_gallery.txt` のようなもの）は**作らない**（特定の画像のメタデータを見る用途の邪魔になるため）。
- **REQ-5.2** txt の中身は **fast_meta CLI の出力と同一のテキスト**とする。ライブラリの整形関数 `extract_to_writer` で生成し、独自ヘッダの付加や整形・要約はしない。`extract_to_writer` に渡すパスは、その画像の**絶対パス**（OS から得た表記）で常に統一する（出力の見出し行にパスが埋め込まれるため、相対／絶対の混在でバイト列が変わると REQ-5.3 の判定が壊れる）。
- **REQ-5.3** 命名と衝突の規則（この順で判定する）。「自ツール製かどうか」の判定はファイル側だけで完結させる：**既存 txt の内容が、今回その画像について生成した出力テキストとバイト一致すれば、自ツールが出したものとみなす**。ただし比較は、出力の先頭にある見出し行（`=== ... File: <パス> ===` の行）を除いた本文で行う（見出しにはパスが埋め込まれるため、フォルダを移動した場合や別表記のパスで到達した場合に、本文が同じでも見出しだけが変わって誤判定になるのを防ぐ）。
  1. `001.txt` が無ければそこに出す（`written`）。
  2. `001.txt` があり、内容が今回の出力とバイト一致する → 自ツール製とみなし、**既定はスキップ**（`skipped_exists`）。`--overwrite` 指定時のみ上書きする（`overwritten`）。
  3. `001.txt` があり、内容が一致しない → 他者のファイルとみなす。退避先の `001_metadata.txt` が**無ければ**そこに出す（`fallback_metadata`）。
  4. `001_metadata.txt` が既にある場合は、書き込む前に手順2と同じ判定を行う：一致すれば自ツール製として既定スキップ／`--overwrite` で上書き。一致しなければ何も書かず、`skipped_exists` としてログに警告を残す（他者のファイルを潰さない）。
- **REQ-5.4** txt を出す条件は「fast_meta がその画像についてレコードを1件以上返したこと」とする。pos/neg 抽出の成否は txt 出力と無関係である（ComfyUI で辿れなかった画像や Stealth のみ保有の画像にも、レコードがある限り txt は出る）。レコードが1件も返らなかった画像（メタデータなし、または読めない画像）については txt を出さない（`txt_status = 'none'`）。
- **REQ-5.5** txt の書き込みに失敗した場合（権限等）は `txt_status = 'failed'` とし、ログにも残す。txt 出力の成否は DB 取り込みの成否と切り離す：txt が書けなくても DB 取り込みは続行し、逆も同様とする。
- **REQ-5.6** Phase 1（DB なし）の段階では `txt_status` は DB ではなくログに記録する。判定規則（REQ-5.3）は Phase 1 から同一とする。ログにはページ単位の `txt_status` を**全ページ分**書く（DB の有無によらず、どのページがどうなったかはログだけで追えるようにする）。
- **REQ-5.7** 同一フォルダ内に同 stem・異拡張子の画像（例：`001.png` と `001.jpg`）が同居する場合、両者が同じ `001.txt` を狙う。この場合も REQ-5.3 を機械的に適用するのが仕様である：先に処理した方（自然順で先のページ）が `001.txt` を取る。もう一方は、本文が一致しなければ `001_metadata.txt` へ退避され、本文が一致すれば（同一画像の形式違い等）手順2により自ツール製とみなされてスキップされる。

## §6 生成元ごとの pos/neg 抽出

### 6.1 抽出元の一覧（フィールドレベル）
- **REQ-6.1** pos/neg の抽出元は形式ごとに以下で固定する。主対象は **NovelAI**（お手本 CG 集の生成元として圧倒的に多い）。

| 生成元 (source) | 格納場所 | pos | neg |
|---|---|---|---|
| novelai | PNG テキストチャンク | `Description` の本文 | `Comment`（JSON）の `uc` |
| a1111 | PNG/JPEG 等の `parameters` テキスト | `Negative prompt:` 行より前 | `Negative prompt:` 行（REQ-6.2） |
| comfyui | `prompt` キー（API 形式 JSON）等 | 辿りによる（REQ-6.4） | 辿りによる（REQ-6.4） |
| swarmui | `sui_image_params`（JSON） | `prompt` | `negativeprompt` |
| invokeai | `invokeai_metadata`（JSON） | `positive_prompt` | `negative_prompt` |
| invokeai（旧 sd-metadata） | PNG `sd-metadata`（JSON） | `image.prompt`（文字列はそのまま／配列は `(<prompt>:<weight>)` を `, ` 連結） | なし（空文字列） |

- NovelAI の補足：`Description` が無い場合は `Comment`（JSON）の `prompt` を pos の代替とする。**NovelAI 判定の条件は「`Comment` が JSON として解析でき、`prompt` キーまたは `uc` キーを含むこと」で固定する**（`Description` 単独では NovelAI と判定しない。`Description` キーは他形式も使うため）。
- **複数候補の優先順位**：1枚の画像に複数の形式の候補が共存する場合は、次の順で「最初に pos が取れた候補」を採用し、`source` はその形式とする。(1) NovelAI（上記の判定条件を満たす場合）→ (2) ComfyUI（`prompt` キーの辿りに成功した場合）→ (3) A1111（`parameters` 系レコード）→ (4) SwarmUI → (5) InvokeAI。どの候補でも pos が取れなければ未抽出とする。
- InvokeAI の旧 `sd-metadata` 形式（Phase 3 で実装）の補足：キー構成は Phase 0 で実物確認済み。`image.prompt` が文字列ならそのまま pos とする。配列 `[{ "prompt": <文字列>, "weight": <数値> }, ...]` なら、各要素を `(<prompt>:<weight>)` として出現順に `, ` で連結する（例：`[{"prompt":"masterpiece","weight":1.0},{"prompt":"1girl","weight":0.8}]` → `(masterpiece:1.0), (1girl:0.8)`）。`weight` が無い（または数値でない）要素は `prompt` のみ、`prompt` が空の要素は飛ばす。連結結果が空なら未抽出。`neg` は常に空文字列（旧形式に負のプロンプトが無いため）。`image.prompt` が文字列でも配列でもない場合は未抽出。`weight` は JSON の数値を serde_json の標準表記で書く（`1.0` は `1.0`、`0.80` は `0.8`）。
- pos を採用して `source = 'unknown'` として取り込むのは、上記の全候補が不成立で、かつ単独の `Description` レコードの本文が存在する場合に限る。その本文を pos とし、neg は空とする。それ以外の場合（生成元が判定できず pos も採用できないページ）も、`source` には §4.3 の定義どおり `unknown` を記録したうえで未抽出とする。
- `source` の決定規則の総括：fast_meta がレコードを1件も返さなかったページは `source = 'none'`。ただし、読み取り自体に失敗したページ（壊れた画像等）は、レコードの有無によらず `source = 'error'` とする（REQ-9.4）。生成元の判定自体ができなかったページ（Stealth レコードのみが返った場合を含む）は `source = 'unknown'`。生成元は判定できたが pos が取れなかったページは、その生成元を `source` に記録したうえで未抽出とする（REQ-6.3）。判定できた生成元が複数あり、どの候補からも pos が取れなかった場合は、複数候補の優先順位で最上位の判定済み生成元を `source` に記録する。生成元の判定は pos の取得成否とは独立に行う（例：`prompt` キーがあれば comfyui、Comment が NovelAI の JSON であれば novelai、と判定する）。

### 6.2 A1111 の分割規則
- **REQ-6.2** `parameters` テキストの分割は次のとおりとする：
  - 行の分割は `\n` で行い、末尾の空行は落とし、各行の末尾の `\r` は除いてから以下の規則を適用する（これは行分割の定義であり、プロンプト本文の正規化ではない）。
  - 末尾の行が `Steps:` で始まる場合は、その行を生成パラメータ行として除去する。
  - `Negative prompt:` で始まる行があれば、**最初に現れた**その行からパラメータ行の直前までを neg とし、それより前を pos とする（同形式の行が複数あっても最初の行でのみ分割する）。
  - `Negative prompt:` 行が無ければ、全体を pos とし neg は空とする。
  - パラメータ行（`Steps:` 行）が無い場合は、`Negative prompt:` 行からテキスト末尾までを neg とする。
  - pos／neg 文字列の再構成：neg は `Negative prompt:` 行の接頭辞を取り除いた残りから始める。複数行の再結合は `\n` で行い、pos／neg とも末尾の改行は含めない（先頭・末尾のその他の空白はそのまま保持する）。

### 6.3 部分抽出の扱い
- **REQ-6.3** **pos が抜ければ「抽出できた」ものとし、neg が無い／抜けない場合は neg = 空文字列とする**（例：NovelAI で `Comment` はあるが `uc` が無い画像、A1111 で `Negative prompt:` 行が無い画像。なお NovelAI で `Comment` 自体が欠け `Description` だけがある画像は、REQ-6.1 の最終規則により `source = 'unknown'` として取り込まれる）。pos が抜けない場合は未抽出とする（`source` には判定できた生成元を記録し、抽出できたかどうかは `prompt_hash` の有無で区別する）。

### 6.4 ComfyUI の辿り（ベストエフォート）
- **REQ-6.4** fast_meta が抽出するのは `prompt`（API 形式のノードグラフ JSON）と `workflow` の raw テキストまでであり、pos/neg への分解は fast_meta の機能ではない。本ツール側で以下の規則で辿る：
  - 対象データ：PNG テキストチャンクの `prompt` キー。また、JPEG／WebP で EXIF UserComment の中身が JSON オブジェクトである場合、および PNG の eXIf 由来 UserComment（REQ-6.7 で ComfyUI 候補に振り分けられたもの）も同じ対象とする。このとき、JSON が `prompt` メンバー（オブジェクト）を持つラッパ形式（`{"prompt": <グラフ>, "workflow": ...}`）であれば、その `prompt` メンバーの中身をグラフとして辿る（メンバーが無ければ JSON 自体をグラフとして扱う）。`workflow`（UI 形式）からの辿りは対象外。
  - サンプラーノードの定義：`class_type` が `KSampler` / `KSamplerAdvanced` のいずれかで、`positive` / `negative` 入力を持つノード。`SamplerCustom` / `SamplerCustomAdvanced` は positive/negative 入力を持たず conditioning は guider 経由になるため、対象外とする。
  - 辿りは**直接リンクのみ**とする：サンプラーノードの `positive`（または `negative`）入力のリンク先ノードが `CLIPTextEncode` であれば、その `inputs.text` を pos（または neg）とする。リンク先が CLIPTextEncode でない場合はそれ以上辿らない（Conditioning 結合等は対象外）。また `inputs.text` 自体が文字列でなく他ノードへのリンクである場合は、その方向は未抽出とする。
  - サンプラーノードが複数ある場合は未抽出とする（どれが本線か決めない）。
  - pos だけ辿れた場合は REQ-6.3 を適用する（抽出済み、neg は空）。
  - 辿れなかった場合は未抽出として扱う。raw は txt に残るので人が読む記録は失われない（DB には raw を保持しない）。失敗しても取り込み全体は止めない。
  - この方式は AI Meta Viewer に実装済みの辿りと同じ考え方だが、実装は本書の上記規則のみに従うこと（外部ツールのコードを根拠に読みに行かない）。

### 6.5 寸法とパラメータ
- **REQ-6.5** 画像の実寸（`pages.width/height`）は fast_meta からは取得できない（ライブラリ API は寸法を返さない）。本ツールがファイルヘッダを直接読んで取得する：PNG は IHDR、JPEG は SOF マーカー、WebP は先頭ヘッダ（VP8/VP8L/VP8X）。どちらの形式として読むかの判定は拡張子ではなく、fast_meta の検出形式（`ScanOutcome.format`）に従う。取得できない場合は NULL とする。NovelAI の `Comment` JSON 内の width/height は生成パラメータであり実寸とは限らないため、実寸として流用しない。
- **REQ-6.6** パラメータ類（seed、steps、cfg、モデル名等）は、行の照合にも segment の同一判定にも使わない。DB 側にも専用列を作らない（必要なら txt を見る）。
- **REQ-6.7** `parameters` キーワードレコード以外のレコードの振り分け：fast_meta の `parameters` キーワードレコードは PNG から届く（テキストチャンク、または末尾付加データの Trailing 経由）。それ以外の経路で届いたレコード（JPEG／WebP の各レコード、および PNG の eXIf 由来レコードを含む）は、中身で振り分ける。振り分けの判定はレコードの Source と keyword の組で行い、**XMP 由来（Source が `*Xmp`）のレコードは振り分け対象外**とする（XMP の `UserComment` 等、同名 keyword のレコードを誤って候補にしないため）。なお REQ-6.1 の「単独の `Description` レコード」は PNG テキストチャンク由来の keyword = `Description` のレコードを指し、XMP 由来の keyword = `description` は含まない：
  - COM セグメント由来のレコードで、本文が `parameters` 形式（REQ-6.2 の分割規則が適用できる形）であれば A1111 候補とする。
  - EXIF UserComment 由来のレコードで、中身が JSON オブジェクトであれば ComfyUI 候補（REQ-6.4 の辿り対象）とし、`parameters` 形式テキストであれば A1111 候補とする。
  - EXIF UserComment 由来の JSON に `sui_image_params` キーがあれば、その値（JSON）を SwarmUI 候補とし、REQ-6.1 の表のキー（`prompt` / `negativeprompt`）で読む。
  - EXIF Model（タグ 0x0110）由来のレコードで、中身が `sui_image_params` を含む JSON であれば SwarmUI 候補とし、同じキーで読む（SwarmUI の旧形式とされるもの。この形式は Phase 0 で実物確認する。未確認の間も候補として実装してよい。実物が存在しなければ、この経路は単に発火しない）。
  - EXIF ImageDescription（タグ 0x010E）由来のレコードで、本文が `parameters` 形式であれば A1111 候補とする。
  - 振り分けた後の優先順位は REQ-6.1 の複数候補の順に従う。

## §7 segment と repeat

### 7.1 segment の定義
- **REQ-7.1** segment とは、ギャラリー内で**同じ pos＋neg が連続する区間（run）**である。取り込みの単位はこの segment であり、segment 1つが配置1つに対応する。
- 同じ pos＋neg が、別の segment を挟んで後で再び現れた場合は、行は再利用するが**配置は別にする**（run をまたいで合算しない）。

### 7.2 同一判定
- **REQ-7.2** 同一判定は pos＋neg の**文字列の完全一致**のみ。正規化（空白・タグ順・表記の正規化）は一切しない。生成はバッチ処理由来であり表記ゆれ自体が発生しにくい、という前提に基づく。
- **REQ-7.3** pos が同じでも neg が違えば別 segment とする。
- **REQ-7.4** seed その他のパラメータは同一判定に入れない（REQ-6.6）。寸法が run の途中で変わっても segment は切らない。segment の寸法は先頭ページの実寸を採用する。

### 7.3 メタデータなし・未抽出ページ
- **REQ-7.5** メタデータが無いページ、または pos を抽出できなかったページは、`pages` には残すが segment を作らず、配置も作らない（`segment_id = NULL`、`prompt_hash = NULL`）。`pages.seq` は全ページに自然順の位置として連続して付くものであり、欠けは生じない。segment を持つページだけを並べると seq が飛んで見えるのは正常である。
- **REQ-7.6** segment を作らないページ（メタデータなし・未抽出・`error`）は run を分断する（その前後で同じ pos＋neg でも別 segment になる）。

### 7.4 repeat への反映
- **REQ-7.7** 取り込み時点で、配置の `repeat` には segment の **run_length を直接セット**する。「候補として保留し人間が承認する」方式は採らない（お手本の配分＝作者がそのシチュエーションに置いた重み、そのものを活かすため）。
- **REQ-7.8** 元の run_length は `segments.run_length` に永久保持する。ユーザーが後で repeat を編集しても、「お手本では何枚だったか」は segment を辿れば常時分かる状態にする。
- ここで言う run_length は「発表された枚数」であって試行回数ではない（§1.2）。難易度や打率への換算はしない。

## §8 起動・設定・ログ

### 8.1 起動形態
- **REQ-8.1** 主経路は exe へのドラッグ＆ドロップである。OS から渡されるフォルダパス群（複数可）を位置引数として受け取り、順に処理する。ターミナルからの CLI 実行も同じ引数仕様で可能とする。
- **REQ-8.2** 対話入力は一切しない（D&D 起動ではコンソールが即時終了し、入力も表示も読めないため）。

### 8.2 設定とオプション
- **REQ-8.3** 設定ファイルは exe と同じフォルダの `sdGalleryImporter.toml` とし、少なくとも `db_path`（取り込み先 SQLite のパス）を持つ。設定ファイル内の相対パスは exe のフォルダ基準で解決する。
- **REQ-8.4** 設定ファイルが無い、または `db_path` が無い場合の既定は、exe と同じフォルダの `story.db` とする（無ければ新規作成する）。設定ファイルが存在するが TOML として解析できない、または `db_path` が文字列でない場合は、既定へフォールバックせず、その旨をログに残して異常終了する（黙って別 DB に書かない）。
- **REQ-8.5** CLI オプションは以下のみとする（設定ファイルより CLI を優先する）：
  - `--db <path>`：取り込み先 DB の上書き。相対パスは設定ファイルと同様に **exe のフォルダ基準**で解決する（D&D 起動時のカレントディレクトリは不定なため、カレントディレクトリ基準にはしない）。
  - `--overwrite`：txt サイドカーの上書きを許可する（REQ-5.3）。ただし上書きできるのは、自ツール製と判定された（内容が一致した）ファイルのみであり、内容が一致しない他者のファイルは `--overwrite` 時でも上書きしない。
  - `--recursive`：サブフォルダを常に子ギャラリーとして再帰処理する（REQ-3.3）。
  - `--dry-run`：txt も DB も書かない。segment 構成・repeat・未抽出をログにだけ出す。dry-run 時は DB の新規作成・スキーマ用意・バックフィル（REQ-4.3）も行わない。DB が既に存在する場合に限り、読み取り専用で開いて取り込み済み判定（§9.1）に使う。DB が存在しない場合、および存在しても本ツールの追加テーブル（`galleries` 等）がまだ無い場合は、スキーマ用意を行わず、全フォルダを未取り込みとして扱う。なお segment 構成・repeat のログ出力は Phase 2 以降の範囲であり、Phase 1 の dry-run は txt 出力予定の一覧のみを出す。dry-run でも REQ-5.3 の判定（既存 txt の読み取りと比較）は行い、ログに載る `txt_status` はその予測結果とする（書き込みだけを行わない）。Phase 2 以降の dry-run では segment 構成・repeat・未抽出も予測としてログに出す。Phase 2 以降の dry-run のログにも全体の合計を載せ、その値は「取り込んだ場合の予測」として REQ-8.10 と同じ数え方で出す（`import_runs` 行自体は作らない）。
  - `--version`：バージョン表示。`--version` が指定された場合は、他のオプションやフォルダ引数の有無にかかわらず、バージョンを表示して終了コード 0 で即終了する。ログファイルは作らず、DB にも触れない。
  - 列挙外のオプション、値を取るオプション（`--db`）の値欠落、`--db` の重複指定は引数エラーとし、ログファイルが作成できる範囲で記録し、終了コード 1 で終了する（DB には触れない）。引数エラー要因と `--version` が同時に指定された場合は、引数エラーを優先し、終了コード 1 で終了する。
- **REQ-8.6** DB が存在しないパスを指定された場合は新規作成し、§4 のスキーマを冪等に用意してから取り込む。DB がロックされている等の理由で開けない場合は、その旨をログに残して異常終了する（黙って別 DB に書くようなことはしない）。

### 8.3 ログ
- **REQ-8.7** 報告はコンソールではなく**ログファイル**に出す。実行ごとに exe と同じフォルダへ `import_YYYYMMDD_HHMMSS.log` を1つ作る（`--dry-run` 時は `import_dryrun_YYYYMMDD_HHMMSS.log`）。同名ファイルが既にある場合は上書きせず、末尾に `_2`、`_3` …を付けて別ファイルにする。exe のフォルダにログファイルを作成できない場合は、カレントディレクトリへの作成を試み、それもできない場合はコンソール出力と終了コードでのみ結果を示し、ログなしで処理を継続する（全体異常の場合はそのまま異常終了する）。
- **REQ-8.8** ログの内容：実行条件（対象フォルダ、DB パス、オプション）、ギャラリーごとのサマリ（ページ数、txt 出力／スキップ数、segment 数）、ページ単位の `txt_status` 全ページ分（REQ-5.6）、未抽出ページの一覧、メタデータなしページ数、失敗したフォルダと理由、全体の合計。ここで「全体の合計」は `import_runs` の集計値（REQ-8.10）と同義とし、新規に取り込んだ分のみを数える（取り込み済みでスキップしたギャラリーは、ギャラリーごとのサマリには現れるが合計には含めない）。ここで Phase 1 の段階の「未抽出ページの一覧」は「メタデータなし／読めなかったページの一覧」を指す（pos 抽出は Phase 2 以降）。加えて、**DB 書き込みを伴う実行（Phase 2 以降、かつ `--dry-run` でない実行）に限り**、生成した story_id を含め、集計値をその実行の `import_runs` 行と一致させる。Phase 1（DB なし）および `--dry-run` では story_id と `import_runs` への言及はログに含めない。Phase 1 では segment 数もログに含めない（抽出・segment 化は Phase 2 以降）。また Phase 1 では、通常実行・`--dry-run` のいずれでも「全体の合計」はログに載せない（DB 取り込みを行わないため、REQ-8.10 の数え方の対象自体が存在しない）。取り込み済みでスキップしたリーフ（REQ-9.2）のサマリに出す segment 数は、再計算せず、既存 DB に記録されているそのギャラリーの segment 数とする。同様に、スキップしたリーフについての未抽出ページの一覧とメタデータなしページ数も、再計算せず既存 DB の `pages`（`prompt_hash` が NULL のもの／`source` が該当するもの）から出す。
- **REQ-8.9** コンソールへは出してもよいが、コンソールが無くても（D&D 起動でも）処理と記録が完結すること。
- **REQ-8.10** `import_runs` 行は、REQ-4.3 のスキーマ用意が成功した**後に** INSERT し（`finished_at` は NULL）、終了時に集計値と `finished_at` を UPDATE する。スキーマ用意の段階で異常終了した実行については `import_runs` 行を作らない（§11 基準10の「変更が残らない」と矛盾させないため）。`log_path` には、実際に作成したログファイルの絶対パスを INSERT 時にそのまま入れる（カレントディレクトリへフォールバックして作った場合はそのパス。ログファイル自体を作成できなかった場合は NULL）。異常終了した実行の行は `finished_at` が NULL のまま残り、それ自体が異常の記録になる。集計値の数え方（いずれも、その実行での分だけ）：`gallery_count` は新規に作成した `galleries` 行の数（リーフとコンテナの両方を含む。再走査しただけの既存コンテナは含まない）。REQ-9.2 の役割不一致により既存のコンテナ行をリーフ化した場合は、行自体は新規作成ではないが、`gallery_count` に数える（リーフとして新規に取り込んだものとして扱い、その pages も `page_count` に数える）。`page_count` は新規に取り込んだリーフの `pages` 総数。`segment_count` は新規に作成した `segments` の数。`unextracted_count` は新規に取り込んだページのうち `prompt_hash` が NULL のものの数（メタデータなし・`error`・未抽出のすべてを含む）。

## §9 再取り込みとエラー処理

### 9.1 再取り込み
- **REQ-9.1** ギャラリーの同一性は `root_path` の一意性で判定する。`root_path` には**正規化済み絶対パス**を格納する。正規化の規則：まず `std::fs::canonicalize` で実パスを解決し（ジャンクション／シンボリックリンク／subst 等の別表記を吸収する）、先頭の `\\?\` プレフィクスを除去し、区切り文字を `\` に統一し、末尾の区切りを（ドライブルートを除き）除去し、全体を小文字化する（Windows のパスは大小文字を区別しないため）。子ギャラリーの `root_path` も文字列連結では組み立てず、そのフォルダ自身に同じ正規化（canonicalize からの一連の手順）を適用して決める（サブフォルダ自体がジャンクションの場合でも実パスで一意になる。`galleries.name` には元の表記のフォルダ名を保持する）。内容のハッシュによる同一性判定はしない。
- **REQ-9.2** 再取り込みの判定は**ギャラリー（リーフ／コンテナ）単位**で行う。取り込み済みのリーフを再度渡された場合は **DB 書き込みのみ**をスキップし、ログに「取り込み済みのためスキップ」と記録する。txt 処理（§5、REQ-5.3 の判定と出力）は通常どおり行う（取り込み後に txt が削除・欠落したギャラリーを再投入すれば txt が復活する）。コンテナを再度渡された場合はコンテナ自体は再利用し、配下を再走査して、未取り込みの子だけを処理する（後から子フォルダが増えた場合に対応するため）。再利用した既存の `galleries` 行の `import_run_id` と `imported_at` は変更しない（最初に取り込んだ実行を指し続ける）。
- 取り込み済みリーフについて、役割が変わらない範囲での内容変化（直下の画像の追加・削除）は検出も追随もしない。DB は変更せず、txt 処理だけが現在のフォルダ内容に対して行われる。取り込み直したい場合は、別フォルダとして渡すか、既存の `galleries` 行を削除してから渡すことになる（本ツールの範囲外の操作）。
- 既存行の役割（リーフ／コンテナ）と、現在のフォルダ内容による判定（REQ-3.2）が食い違う場合の規則：既存行がコンテナ（`story_id = NULL`）で現在はリーフと判定された場合は、その行をリーフとして取り込む（下書きストーリーを後付けで生成する）。この変換の場合は、その行の `import_run_id` と `imported_at` を変換した実行のものに更新する（リーフとしての新規取り込みだからであり、前段の「変更しない」規則は再利用＝スキップ／再走査の場合のものである）。既存行がリーフ（story あり）で現在はコンテナと判定された場合は、リーフとしての取り込み済みを優先し、DB 書き込みは行わず、配下の子走査のみを行う（`--recursive` の混成形と同じ扱い）。`--recursive` 指定時は、取り込み済みリーフであっても配下の子走査は行う（リーフ自体の DB 再取り込みはしない）。
- **REQ-9.3** フォルダを移動したら別ギャラリーとして扱う（パスが変わるため）。これは仕様であり、移動前の gallery との紐付け直しは本ツールの範囲外とする。

### 9.2 エラー処理
- **REQ-9.4** 以下のいずれも「取り込み全体のエラー」にしない。該当ページ／フォルダを記録して続行する：
  - メタデータなし画像、pos 未抽出（§7.3）。
  - txt が書けない（REQ-5.5）。
  - 画像ファイルが壊れていて fast_meta が読めない（`source = 'error'` のページとして記録する）。
  - 1リーフ分の DB 書き込みが失敗した場合（制約違反等）。そのリーフはロールバックし（REQ-4.4）、理由をログに残して、そのリーフだけを失敗として記録し、兄弟リーフを含む残りの処理を続行する。
- **REQ-9.5** 全体を止めるのは次の場合だけとする：DB が開けない場合（REQ-8.6）、設定ファイルが不正な場合（REQ-8.4）、スキーマ用意が失敗した場合（REQ-4.3）、有効なフォルダ引数が1つも無い場合（存在しないパスや、フォルダでない引数しか渡されなかった場合を含む）、引数エラーの場合（REQ-8.5）。その場合もログは残す。終了コードは、正常終了（1フォルダの失敗やスキップを含む）は 0、全体異常は 1 とする。

## §11 受け入れ基準

1. D&D 相当の起動で、複数の sorter 整理済みフォルダを一括処理でき、1フォルダの失敗が他を止めない。同一フォルダの重複指定・ファイルの引数・空フォルダが混ざっても処理が完結する。
2. 各ギャラリー内で、レコードがある画像については画像ごとのサイドカー txt が fast_meta 出力と同一の内容で置かれ（レコードが無い画像には txt は無い）、索引ファイル（`_gallery.txt` 等）は存在しない。既存 txt との衝突時は REQ-5.3 の順（バイト一致判定 → `_metadata` 退避 → 既定スキップ／`--overwrite`）で処理される。
3. 取り込んだギャラリーについて、DB 上で「ギャラリー → ページ（自然順）→ segment（run）→ 配置（repeat = run_length）→ 下書きストーリー」が辿れる。コンテナギャラリーにはストーリーが無い（`--recursive` でリーフ兼用になったもの、REQ-9.2 の役割不一致によりリーフ行が親になったもの、および同じく役割不一致によりコンテナ行がリーフ化したものを除く）。子ギャラリーから辿れる。
4. pos が同じで neg が違う画像は、別 segment・別行になる。pos＋neg が完全一致する連続 run は1 segment にまとまる。正規化による誤合体が無い。pos のみ抽出できたページは neg = 空で抽出済みとして扱われる。
5. メタデータなし／未抽出ページは pages に残り、segment と配置は作られず、その前後で run が分断される。取り込みは止まらない。
6. フォルダ内容が変わっていない同じフォルダの再取り込みでは、galleries / pages / segments / lines / stories / placements が増えず、txt も既定では上書きされない（REQ-9.2 の役割不一致に該当する場合はこの限りでない）。コンテナ配下に増えた子フォルダは、コンテナの再投入で取り込める。
7. seed を含むパラメータの違いだけでは segment も行も分かれない。
8. 実行ごとにログファイルが残り、未抽出・スキップ・失敗がそこから追える（REQ-8.7 のフォールバックによりログファイル自体を作成できなかった場合を除く）。コンソールなしでも完結する。
9. 画像ファイルが移動・改変されていない（取り込み前後のファイル一覧とハッシュが一致する）。
10. 既存行を持つ DB では起動時に `prompt_hash` がバックフィルされ、その行が照合に掛かる。同一 pos+neg の既存行が重複している DB でも異常終了せず、警告をログに残して取り込みが続行される（照合は最小 id の行を採用）。スキーマ用意そのものが失敗した場合は、DB はロールバックされて変更が残らない。
11. 同じフォルダを大小文字違い・末尾スラッシュ違い・ジャンクション経由で指定しても、同一ギャラリーとして判定され、二重取り込みにならない。

## §12 確定事項の一覧（経緯メモ）

本書の設計判断はユーザーとの対話で以下のとおり確定したものである。実装時に迷ったらこの表と各 § の REQ を優先する。

| # | 決定 | 根拠・補足 |
|---|---|---|
| 1 | 供給源は売り物の CG 集（お手本） | 自分の生成物の山ではない。そのまま使えるものを取り込むのが焦点 |
| 2 | 試行回数・難易度は推定しない | ハズレ除去済みのため復元不能（§1.2） |
| 3 | segment = 同じ pos+neg の連続 run、run_length が重み | グラビアが同じポーズを何枚も連ねるのと同じ。合計ではなく連続回数が単位 |
| 4 | repeat には run_length を直接セット | 候補保留＋人間承認は採らない（REQ-7.7） |
| 5 | txt は画像ごとのサイドカー、索引ファイルなし | 特定の画像のメタデータをすぐ見る用途が優先 |
| 6 | txt と DB 化は同時に行う | txt だけ／DB だけ、にしない |
| 7 | txt 衝突：既存 txt が今回の出力と（見出し行を除いて）バイト一致すれば自ツール製として既定スキップ、一致しなければ他者のものとして `_metadata` へ退避。`_metadata` 側も同じ判定で、一致しなければ何も書かず他者として保護する。上書きはオプション時のみ | REQ-5.3 |
| 8 | ページ順はファイル名の自然順のみ | リネームしない（定義は REQ-3.7） |
| 9 | seed は参照しない | 同じモデル／ワークフローを使わないため |
